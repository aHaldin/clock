# Podcast House clock

A Next.js app for engineer PIN clocking, admin timesheets, CSV export, engineer management and audited corrections. Built for **GitHub → Netlify**, with a persistent PostgreSQL database. Server timestamps are UTC milliseconds; screens and exports display Europe/London time including daylight saving. No break deductions or hour rounding.

## Deploy on Netlify

1. Import `aHaldin/clock` from GitHub and select `main`.
2. Use the committed `netlify.toml`: Node 22, build command `npm run build`, publish directory `.next`. Netlify supplies its official Next.js adapter automatically. Do not use a static export.
3. Set these **secret environment variables for Functions/runtime** before using the app:
   - `ADMIN_PASSWORD_HASH`: the salted verifier generated by `npm run setup:env`. Paste the entire unescaped value, including dollar signs. Never use a `NEXT_PUBLIC_` variable.
   - `PIN_PEPPER`: a random secret generated by the same command. Keep it stable; changing it invalidates existing engineer PINs.
4. Keep `BROWSER_CLOCKING=true` (the default). This enables admin-approved browser access without certificates. Do not enable `LOCAL_CLOCKING` in production.
5. Deploy. The `@netlify/database` dependency enables Netlify Database provisioning. Confirm the database appears under **Data & Storage → Database** and supplies `NETLIFY_DB_URL`. Netlify automatically applies SQL migrations from `netlify/database/migrations` before publishing. If your account requires a provisioning action, complete it there and redeploy. Database availability, limits and billing depend on your Netlify account.
6. Open `/admin`, use your configured admin password, add an engineer and six-digit PIN, then choose **Clocking access → Approve this browser** on the intended clocking computer. Sign out of admin and open `/` to clock in.

The supplied source includes no default password, private secrets, engineers or time records. An ignored `.env.netlify` file may have been prepared on the original laptop with its existing password verifier and PIN secret; it must never be added to GitHub. Copy those values into Netlify to retain the chosen admin password. Environment variables configured on the previous hosting provider do not transfer to Netlify.

The hosted database starts empty. Existing SQLite/D1 records on the original laptop remain in `.wrangler/state` and have **not** been migrated. Preserve a backup before any data migration. Do not run the legacy SQLite migrations in `drizzle/` against Postgres; they remain solely as test fixtures.

## Login origin checks

Requests accept the exact configured application origin, Netlify's runtime `URL` / `SITE_NAME`, and the deployment URLs embedded at build time. No wildcard Netlify domains or caller-controlled forwarded headers are trusted. For an additional custom domain, set `APP_ORIGIN` to its full HTTPS origin and redeploy. An origin error happens before password validation.

## Browser approval and admin access

Clocking requires both an active engineer PIN and an admin-issued browser cookie, checked on every server request. The URL and a PIN alone are insufficient. The cookie is random, stored only as a hash in the database, HttpOnly, Secure, SameSite=Strict and valid for one year. Clear cookies to remove it locally, or revoke it through **Clocking access → Manage** to reject it server-side and invalidate pending engineer sessions. Remote admin login does not itself approve clocking access.

This is **browser approval, not a hardware certificate**. An admin can approve any browser, including a phone. Copying a browser credential could transfer clocking access until revoked. It does not prove physical presence in the studio. Certificate-enforced Mac identity from the earlier design is not configured for this deployment. This alternative implements the subsequent request to work without certificates.

Admin uses a separate password with salted PBKDF2-SHA256 verification and eight-hour server sessions. Changing the verifier invalidates old admin sessions. Failed PIN and admin attempts are rate-limited. Engineer sessions expire after 45 seconds and cannot access reports or admin endpoints. Sign out of admin on shared machines.

## Local development

Requires Node 22.13 or later and a PostgreSQL database with the `btree_gist` extension available.

```sh
npm ci
npm run setup:env
# Set DATABASE_URL in the ignored .env.local file.
npm run db:migrate
npm run dev
```

The password prompt hides input. `.env.local` contains an escaped verifier for Next.js dotenv expansion; `.env.netlify` contains the unescaped value for Netlify. Neither belongs in source control. To use HTTP loopback locally, set `BROWSER_CLOCKING=false` and `LOCAL_CLOCKING=true` in `.env.local`; production ignores that bypass. Otherwise browser enrollment requires HTTPS.

`db:migrate` is for a separate/local database. Do not run it on a Netlify database whose migrations are managed by Netlify; each system has its own migration ledger. Keep this project outside a cloud-offloaded folder if local startup stalls while files download.

## Data integrity and testing

Postgres exclusion constraints prevent overlapping shifts, including concurrent inserts and corrections. A unique index permits one open shift per engineer. Clock mutations and corrections use transactions, and server-side session consumption prevents repeated actions. An audit trigger captures the original clock-in. Corrections require a reason, preserve before/after values, and reject stale versions. Database triggers reject changes, deletes and truncation of audit records by ordinary application statements.

```sh
npm test
npm run typecheck
npm run build
```

Tests run the service against both the original in-memory SQLite fixture and a PostgreSQL engine via PGlite, covering PINs, duplicate clock actions, access control, DST/overnight calculations, browser approval/revocation, corrections and audit preservation. Production network concurrency and a complete deployed Netlify acceptance test remain separate checks.

## Backup and restore

Use Netlify Database recovery/backup features for the deployed database. Also keep encrypted exports outside the repository, using PostgreSQL tools and a connection string supplied securely by your deployment operator:

```sh
# DATABASE_URL must be set privately in this shell, never pasted into source.
pg_dump --dbname="$DATABASE_URL" --format=custom --file=/secure/path/podcast-house.dump
# Restore to a NEW empty test database, never directly over live data.
pg_restore --dbname="$RESTORE_DATABASE_URL" --no-owner --no-acl /secure/path/podcast-house.dump
```

Keep `PIN_PEPPER` and the admin verifier backed up separately in a secret manager. Test restoration, row counts, audit history and sample hour totals before switching connections. Securely remove restored engineer/admin sessions before allowing users into a recovered environment. Do not auto-delete originals or audit history. CSV is a report, not a full database backup.
