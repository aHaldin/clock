# Podcast House clock

A Next.js app for engineer PIN clocking, admin timesheets, CSV export, engineer management and audited corrections. Built for **GitHub → Netlify**, with a persistent PostgreSQL database. Server timestamps are UTC milliseconds; screens and exports display Europe/London time including daylight saving. No break deductions or hour rounding.

## Deploy on Netlify

1. Import `aHaldin/clock` from GitHub and select `main`.
2. Use the committed `netlify.toml`: Node 22, build command `npm run build`, publish directory `.next`. Netlify supplies its official Next.js adapter automatically. Do not use a static export.
3. Set these **secret environment variables for Functions/runtime** before using the app:
   - `ADMIN_PASSWORD_HASH`: the salted verifier generated by `npm run setup:env`. Paste the entire unescaped value, including dollar signs. Never use a `NEXT_PUBLIC_` variable.
   - `PIN_PEPPER`: a random secret generated by the same command. Keep it stable; changing it invalidates existing engineer PINs.
4. Keep `ANY_DEVICE_CLOCKING=true` (the default). Any device can use an active engineer PIN; location permission is mandatory for clock-in and clock-out. No certificate or browser approval is needed. Do not enable `LOCAL_CLOCKING` in production.
5. Deploy. The `@netlify/database` dependency enables Netlify Database provisioning. Confirm the database appears under **Data & Storage → Database** and supplies `NETLIFY_DB_URL`. Netlify automatically applies SQL migrations from `netlify/database/migrations` before publishing. If your account requires a provisioning action, complete it there and redeploy. Database availability, limits and billing depend on your Netlify account.
6. Open `/admin`, use your configured admin password, add an engineer and six-digit PIN, sign out of admin and open `/` to clock in. Allow location access when prompted. On Macs, enable Location Services for your browser in System Settings → Privacy & Security → Location Services, and allow location for the site in browser settings.

The supplied source includes no default password, private secrets, engineers or time records. An ignored `.env.netlify` file may have been prepared on the original laptop with its existing password verifier and PIN secret; it must never be added to GitHub. Copy those values into Netlify to retain the chosen admin password. Environment variables configured on the previous hosting provider do not transfer to Netlify.

The hosted database starts empty. Existing SQLite/D1 records on the original laptop remain in `.wrangler/state` and have **not** been migrated. Preserve a backup before any data migration. Do not run the legacy SQLite migrations in `drizzle/` against Postgres; they remain solely as test fixtures.

[Netlify Next.js documentation](https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/) · [Database provisioning and connection](https://docs.netlify.com/build/data-and-storage/netlify-database/tooling/) · [Automatic migrations](https://docs.netlify.com/build/data-and-storage/netlify-database/migrations/)

## Login origin checks

Requests accept the exact configured application origin, Netlify's runtime `URL` / `SITE_NAME`, and the deployment URLs embedded at build time. No wildcard Netlify domains or caller-controlled forwarded headers are trusted. For an additional custom domain, set `APP_ORIGIN` to its full HTTPS origin and redeploy. An origin error happens before password validation.

## Location and clocking access

Any device can clock with a valid engineer PIN. Location permission is mandatory on both actions. The server validates fresh coordinates (within two minutes), geographic ranges and nonnegative accuracy before saving. A permission refusal, timeout or unavailable position leaves the shift unchanged. HTTPS is required outside localhost. Laptops may give less accurate results than phones; the app displays the browser-reported accuracy radius rather than inventing a precise address. Device time must be reasonably correct for freshness validation.

The browser requests location only after clicking Clock in or Clock out. Coordinates, accuracy, client capture time and server event time are saved atomically with the shift. Locations are visible only through admin reports and CSV exports. View location opens Google Maps with those coordinates only when the admin clicks. Old records have no location; corrections preserve the original location and event time. Immutable location rows are included in full database backups. Define a staff notice and retention policy before live use; no background tracking occurs.

Location is self-reported by the browser, can be spoofed, and is not proof of studio attendance. There is no geofence. Certificates are not enforced in this mode. A signed HttpOnly cookie binds short-lived engineer sessions to a browser without granting admin access. PIN failures are limited per browser (five per 15 minutes), with a shared ceiling of 100 attempts per 15 minutes to limit cookie-reset evasion. Successful PIN validation removes its attempt count; a shared ceiling can temporarily block everyone during abuse.

For the retained restricted modes, set `ANY_DEVICE_CLOCKING=false`: `BROWSER_CLOCKING=true` requires admin approval under Clocking access, while `BROWSER_CLOCKING=false` uses the separate certificate gateway described in `deployment/`. Merely changing a flag does not install certificates or configure the gateway. Location remains required for clocking through the application API in all modes.

Admin uses a separate password with salted PBKDF2-SHA256 verification and eight-hour server sessions. Changing the verifier invalidates old admin sessions. Failed PIN and admin attempts are rate-limited. Engineer sessions expire after 45 seconds and cannot access reports or admin endpoints. Sign out of admin on shared machines.

## Local development

Requires Node 22.13 or later and a PostgreSQL database with the `btree_gist` extension available.

```sh
npm ci
npm run setup:env
# Set DATABASE_URL in the ignored .env.local file.
npm run db:migrate
npm run dev
```

The password prompt hides input. `.env.local` contains an escaped verifier for Next.js dotenv expansion; `.env.netlify` contains the unescaped value for Netlify. Neither belongs in source control. To use HTTP loopback locally, keep `ANY_DEVICE_CLOCKING=true` and set `LOCAL_CLOCKING=true` in `.env.local` for local session cookies; production ignores the local HTTP exception. Location still requires device/browser permission.

`db:migrate` is for a separate/local database. Do not run it on a Netlify database whose migrations are managed by Netlify; each system has its own migration ledger. Keep this project outside a cloud-offloaded folder if local startup stalls while files download.

## Data integrity and testing

Postgres exclusion constraints prevent overlapping shifts, including concurrent inserts and corrections. A unique index permits one open shift per engineer. Clock mutations and corrections use transactions, and server-side session consumption prevents repeated actions. An audit trigger captures the original clock-in. Corrections require a reason, preserve before/after values, and reject stale versions. Database triggers reject changes, deletes and truncation of audit records by ordinary application statements.

```sh
npm test
npm run typecheck
npm run build
```

Tests run the service against both the original in-memory SQLite fixture and a PostgreSQL engine via PGlite, covering PINs, duplicate clock actions, access control, DST/overnight calculations, browser approval/revocation, corrections, audit preservation, any-device sessions, mandatory location validation, immutable location records, and geolocation failures. Production network concurrency and a complete deployed Netlify acceptance test remain separate checks.

## Backup and restore

Use Netlify Database recovery/backup features for the deployed database. Also keep encrypted exports outside the repository, using PostgreSQL tools and a connection string supplied securely by your deployment operator:

```sh
# DATABASE_URL must be set privately in this shell, never pasted into source.
pg_dump --dbname="$DATABASE_URL" --format=custom --file=/secure/path/podcast-house.dump
# Restore to a NEW empty test database, never directly over live data.
pg_restore --dbname="$RESTORE_DATABASE_URL" --no-owner --no-acl /secure/path/podcast-house.dump
```

Keep `PIN_PEPPER` and the admin verifier backed up separately in a secret manager. Test restoration, row counts, audit history and sample hour totals before switching connections. Securely remove restored engineer/admin sessions before allowing users into a recovered environment. Do not auto-delete originals or audit history. CSV is a report, not a full database backup.

## Deploying the location update

These changes require migration `0002_locations.sql` before the new app handles clock events. Netlify applies committed migrations during deployment; for a separate database use the documented migration command. Keep the existing `ADMIN_PASSWORD_HASH` and `PIN_PEPPER`; the update does not reset passwords or engineer PINs. Import the private `.env.netlify` into Netlify Functions/runtime settings if those values are missing. Do not enter a plaintext password as `ADMIN_PASSWORD_HASH`. After deployment test a real phone and Mac: allow location, clock in/out, check the admin map/accuracy, then deny location and confirm no entry is saved.
